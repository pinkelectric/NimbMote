# NimbMote repository rules

## Обязательный Git-процесс

1. Перед каждым существенным изменением выполнить `git status` и проверить
   последний commit. Предыдущая рабочая версия должна быть сохранена отдельным
   commit до начала новой работы.
2. Не смешивать новую задачу с незакоммиченными изменениями предыдущей задачи.
   Не удалять и не перезаписывать пользовательские изменения ради чистого
   состояния репозитория.
3. Исходники и история изменений хранятся в Git. Не создавать копии дерева
   исходников по версиям.
4. Основная ветка локального проекта — `main`. Commit должен описывать одну
   законченную логическую работу и оставлять проект в проверяемом состоянии.

## Версии и теги

1. Единственный источник версии — файл `VERSION` в корне репозитория. Формат:
   `MAJOR.MINOR.PATCH` без префикса `v`.
2. Android `versionName`/`versionCode` и Windows assembly/file/product version
   должны вычисляться из `VERSION`; нельзя задавать расходящиеся версии вручную.
3. Для стабильной тестовой сборки создавать аннотированный Git tag строго в
   формате `vMAJOR.MINOR.PATCH`, например `v0.1.0`, `v0.1.1`, `v0.2.0`.
4. Tag создаётся только на commit, для которого обе платформы успешно собраны,
   release-артефакты проверены, а CHANGELOG соответствует этой версии.
5. PATCH увеличивается для совместимых исправлений, MINOR — для новых функций,
   MAJOR — для несовместимых изменений протокола или поведения.

## Каталог releases

1. Для версии, предназначенной для реальной установки и тестирования, создавать
   `releases/vMAJOR.MINOR.PATCH/`.
2. В подпапке версии допускаются только три готовых файла:
   versioned debug APK, нативный Windows Setup EXE и `CHANGELOG.md`. Portable
   ZIP допустим только как внутренний вход сборки Setup и не является
   пользовательским release-артефактом.
   Для installer-only PATCH без изменений Android допускаются только новый Setup
   EXE и `CHANGELOG.md`; APK наследуется от предыдущей версии и не пересобирается.
3. Не помещать в `releases` исходники, SDK, кэши, `build`, `bin`, `obj` или полную
   копию репозитория.
4. CHANGELOG должен кратко описывать изменения, статус проверок и SHA-256 обоих
   бинарных артефактов.
5. Перед началом следующей версии убедиться, что release commit сохранён, tag
   указывает на него и `git status` не содержит незавершённых изменений.
